Query optimization is a crucial aspect of database management, ensuring that queries execute efficiently by reducing the time and resources required.
It involves analyzing queries and selecting the best execution plan based on factors like indexes, join methods, and available system resources.
proper indexing, reducing table scans, and using optimized query syntax can significantly improve database performance, especially for large datasets.

Create a Sample Table with 1 million Rows
CREATE TABLE employee_data (
    employee_id SERIAL PRIMARY KEY,
    name VARCHAR(50),
    department VARCHAR(50),
    salary INTEGER,
    age INTEGER,
    joining_date DATE
);

-- Insert 1 million rows
INSERT INTO employee_data (name, department, salary, age, joining_date)
SELECT 
    'Employee' || i, 
    CASE WHEN i % 5 = 0 THEN 'Sales' 
         WHEN i % 5 = 1 THEN 'Engineering' 
         WHEN i % 5 = 2 THEN 'HR' 
         WHEN i % 5 = 3 THEN 'Finance' 
         ELSE 'Admin' END,
    (RANDOM() * 100000)::INTEGER,
    (RANDOM() * 50 + 20)::INTEGER,
    NOW() - (RANDOM() * INTERVAL '10 years')
FROM generate_series(1, 1000000) AS i;

Applying Different Types of Indexes

B-Tree Index (default for ordered searches)

Hash Index (efficient for equality searches)

GIN (Generalized Inverted Index) (useful for multi-valued fields or full-text search)

BRIN (Block Range Index) (best for large datasets with sequential data)

GiST (Generalized Search Tree) (useful for spatial or range queries)

Partial Index (index only a subset of rows, e.g., high-salary employees)

Best practices for query optimization
Avoid using wildcard characters
Limit the number of returned rows
Use appropriate data types
Enable slow query logging
- Logging_collector = ‘on’
- log_min_duration_statement = 1000
Update table stats with VACUUM
VACUUM analyze orders;
copy vs insert
Use COPY when loading large volumes of data quickly, such as initial data imports or bulk loading from files.
Use INSERT for smaller, ad-hoc inserts or when inserting data row-by-row programmatically in an application.
Create indexes on columns used in join conditions
Filter data before performing joins using where clauses
Partition large tables to improve join performance
Use parallel query which allows PostgreSQL to utilize multiple CPU cores for a single query
Use partitioning such as range partitioning, list partitioning (divides data based on a list of discrete values), hash partitioning (distribute rows evenly)
Example of List Partitioning
Let’s consider a table named orders that we want to partition by country.

Create the Partitioned Table

CREATE TABLE orders (
    order_id SERIAL,
    customer_name TEXT,
    amount DECIMAL(10, 2),
    country TEXT,
    PRIMARY KEY (order_id, country)  -- include the country column in the primary key
) PARTITION BY LIST (country);
Create Partitions Based on List Values

CREATE TABLE orders_usa PARTITION OF orders FOR VALUES IN ('USA');
CREATE TABLE orders_canada PARTITION OF orders FOR VALUES IN ('Canada');
CREATE TABLE orders_mexico PARTITION OF orders FOR VALUES IN ('Mexico');
Insert Data and Test Query Performance

Now, when you insert data into the orders table, rows automatically go to the correct partition based on the country value:

INSERT INTO orders (customer_name, amount, country) VALUES ('Alice', 100, 'USA');
INSERT INTO orders (customer_name, amount, country) VALUES ('Bob', 200, 'Canada');
INSERT INTO orders (customer_name, amount, country) VALUES ('Carlos', 150, 'Mexico');
If you query orders from Canada, PostgreSQL only scans the orders_canada partition:
