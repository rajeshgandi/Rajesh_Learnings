
10 PostgreSQL Settings That Instantly Boost Performance (No Code Changes)⚡️ 🚀 
Performance tuning doesn't always require rewriting SQL or scaling up your infrastructure.Sometimes, the biggest gains come from simply tuning PostgreSQL’s configuration parameters — especially when you’re still running on defaults.
👉 Whether you’re running PostgreSQL on-premises or on AWS RDS, these 10 carefully selected settings can help you:
✅ Improve query performance
✅ Reduce I/O pressure
✅ Prevent table bloat
✅ And do all of this — without touching application code 😃 .
These are the same parameters I’ve used in real-world production environments to significantly reduce latency and stabilize workloads.

🔧 1. shared_buffers
PostgreSQL’s internal memory cache.
🧠 Best Practice: Set to 25–40% of total system memory.

Example: For a 16 GB server → shared_buffers = 4GB

🔧 2. work_mem
Memory for sorting, hash joins, etc. Set too low and queries spill to disk.
🧠 Best Practice: 4MB–64MB depending on workload and available RAM.

Apply per session or use SET work_mem = '64MB'; for heavy queries.

🔧 3. effective_cache_size
Tells PostgreSQL how much OS cache is available.
🧠 Best Practice: 70–80% of RAM

🔧 4. maintenance_work_mem
Used for VACUUM, CREATE INDEX, CLUSTER.
🧠 Best Practice: 256MB – 2GB depending on table size

🔧 5. autovacuum_vacuum_threshold & autovacuum_vacuum_scale_factor
Control how aggressively autovacuum cleans dead tuples.
🧠 Best Practice:

autovacuum_vacuum_threshold = 50
autovacuum_vacuum_scale_factor = 0.05
Prevents table bloat and transaction ID wraparound.

🔧 6. log_min_duration_statement
Log queries that run longer than a threshold.
🧠 Best Practice: Start with 500ms or 1000ms

🔧 7. random_page_cost
Planner setting: cost of non-sequential reads.
🧠 Best Practice:
Set to 1.1 or 1.2 if using SSDs
Default (4.0) assumes slow-spinning disks.

🔧 8. temp_file_limit
Prevents queries from consuming excessive disk for temporary files.
🧠 Best Practice: 1–5 GB depending on workload and disk space.

🔧 9. checkpoint_completion_target
Spreads out checkpoints over time to reduce I/O spikes.
🧠 Best Practice: Set to 0.7–0.9

🔧 10. max_parallel_workers_per_gather
Enables parallelism for large queries.
🧠 Best Practice: Start with 2–4 for OLAP/analytical workloads

✅ Real-World Impact
In one of our production PostgreSQL environments, tuning just a few of these parameters (work_mem, autovacuum settings, and enabling parallel workers) improved query performance by 50–60% without touching a single line of application code.
Query latency dropped from 11s ➝ 3.2s, and disk usage stabilized after vacuum tuning.

🐘 🚀 PostgreSQL Performance Issue: Slow Queries Due to Autovacuum Misconfiguration⚠️ 🚀 

🎯 Real Scenario:
In one of our production PostgreSQL databases, routine SELECT queries that usually completed in 300–400ms suddenly started taking 12–15 seconds — without any code changes.
This unexpected latency spike signaled something deeper happening under the hood.

🔍 Investigation:
We used the following queries to start digging:

SELECT relname, n_dead_tup 
FROM pg_stat_user_tables 
ORDER BY n_dead_tup DESC;

We found millions of dead tuples in key transactional tables.
Next, we checked the autovacuum settings:

SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;

✅They were still at the default values:

⚠️ Root Cause:
PostgreSQL’s autovacuum daemon was not running frequently enough, allowing dead tuples to pile up, which caused:

✅Table and index bloat
Poor planner estimates
Slower sequential and index scans

✅ What We Did:
Lowered autovacuum thresholds for high-write tables:

ALTER TABLE transactions SET (
 autovacuum_vacuum_threshold = 50,
 autovacuum_vacuum_scale_factor = 0.02
);

Ran a manual VACUUM FULL during low-traffic hours:
VACUUM FULL transactions;

Added fillfactor = 80 for update-heavy tables to reduce future bloat:

ALTER TABLE transactions SET (fillfactor = 80);
✅Enabled logging for analysis:
log_autovacuum_min_duration = 0

🚀 Results:
✅ Query latency dropped from 15s ➝ under 800ms
✅ Reclaimed over 60 GB of disk space
✅ Autovacuum now kicks in proactively

💡 Best Practices Learned:
🔁 Always monitor dead tuples in high-write tables.
⚙️ Tune autovacuum based on workload — default isn't enough.
🧼 Use VACUUM FULL or pg_repack for bloated tables.
📊 Set log_autovacuum_min_duration = 0 (at least in non-prod) to catch issues early.
📌 Add fillfactor for update-heavy tables to reduce row churn.

🧠 Final Thought:
PostgreSQL is powerful, but only when configured thoughtfully.
Autovacuum is your silent hero — if you don’t tune it, it may betray you silently.
